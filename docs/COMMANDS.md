# ASA command reference and deterministic router

TSTerm 0.5.x includes a structured ASA command catalog, hybrid retrieval, and a JSON-schema router that
selects a command record and extracts parameters. The model never writes the final command string.

## What is in the catalog

TSTerm loads two local packs:

| File | Records | Purpose |
| --- | --- | --- |
| `resources/commands/asa-commands.json` | 503 | Curated, parameterized, fillable commands |
| `resources/commands/asa-reference.json` | 2,510 | Cisco documentation reference entries |

The curated file is generated by `scripts/build-asa-command-catalog.mjs` from:

- the 75 top-level commands in `src/shared/asa-commands.ts`, and
- every command, verify step, and cleanup step in the 77 ASA runbooks in
  `resources/catalog/cisco-asa.json`.

| Curated kind | Count | Notes |
| --- | --- | --- |
| Top-level ASA commands | 75 | Browsable, but incomplete without a subcommand |
| Runbook commands | 407 | Concrete troubleshooting commands with parameters and cleanup |
| Complete examples from ASA help | 21 | Literal examples such as `write memory` and `copy running-config startup-config` |

The reference file is generated by `scripts/import-asa-command-reference.mjs`, which reads Cisco's public
**Cisco Secure Firewall ASA Series Command Reference** (A–H, I–R, S, and T–Z). Each entry contains the
command name, documented syntax, supported modes, a short description, risk classification, source book,
and the Cisco URL. Descriptions and examples are intentionally reduced; the official page remains the
source of truth. Reference entries are searchable and copyable but **not fillable** because their syntax
is not parameterized.

The next data phase is to parameterize the high-value reference commands, crawl the live ASA `?` help for
device-specific syntax, and add syslog-ID mappings.

Each record has:

```ts
interface AsaCommandRecord {
  id: string
  vendor: 'cisco-asa'
  commandTemplate: string          // no model-generated command text
  description: string
  category: string
  mode: string
  risk: 'read_only' | 'diagnostic' | 'mutating' | 'destructive'
  keywords: string[]
  parameters: CommandParameter[]   // name, required, regex, default, description
  examples: string[]
  cleanup: string[]                // required for diagnostic commands
  source: 'asa-help' | 'runbook' | 'cisco-docs' | 'device-help'
  version: string
  syntax?: string                  // documented syntax for reference entries
  modes?: string[]
  url?: string                     // Cisco documentation page
  book?: string                    // A-H, I-R, S, or T-Z
  referenceOnly?: boolean          // excluded from Fill and AI routing
}
```

## Retrieval

### BM25

The main process builds an in-memory BM25 index at startup. It:

- lowercases, tokenizes `%ASA-4-106023`, command paths, flags, interfaces, IPs, and dotted tokens;
- keeps the full token and its parts;
- applies a small stemmer so `hosts`, `host`, `interfaces`, and `interface` match;
- weights the command template, documented syntax, keywords, description, examples, cleanup, and mode;
- filters by risk and mode before ranking;
- boosts exact command phrases, the command name, the first step of a runbook workflow, and parameter
  intent (host vs port vs subnet);
- de-duplicates identical command templates.

BM25 is always available and needs no AI or network access.

### Vector index

The vector layer is optional and local:

- model: `nomic-embed-text` through Ollama;
- endpoint: `/api/embed`, with a fallback to `/api/embeddings` for older Ollama builds;
- coverage: the **503 fillable records only**; the 2,510 documentation entries stay BM25-only;
- text embedded: command template, description, keywords, examples, and cleanup;
- storage: `<userData>/command-index/nomic-embed-text.json`, keyed by record id and content hash;
- build: **Build vector index** in the command browser, or `commands.buildIndex()` over IPC;
- query: one embedding per search, cosine similarity in memory.

The fillable set does not need LanceDB, Chroma, Torch, or a Python service.

### Fusion

BM25 and vector lists are merged with Reciprocal Rank Fusion (`k = 60`). The browser shows whether a
result came from `bm25`, `vector`, or `hybrid`.

### Free chat and follow-up retrieval

Free chat uses the same local catalog in addition to the runbook hints:

- the top five hybrid matches are added to the system prompt as `commandHints`;
- documentation reference entries are labelled as not device-verified (and are excluded from free-chat hints
  when strict command grounding is on);
- runbook hints use partial, stemmed matching, so a natural-language question no longer
  has to contain every word from a runbook;
- follow-up questions add `%ASA-...` syslog IDs and the last command line from the terminal to the local
  retrieval query, so “why did that fail?” can find the right runbook or reference;
- live terminal output remains opt-in and is still marked untrusted in the prompt.

### Assistant command grounding

Every command that appears in an assistant reply — fenced or inline — is checked against the local catalog
before it can be filled. The renderer calls `commands.verify()` and shows one of three states:

| State | Meaning | Fill |
| --- | --- | --- |
| `verified` | Exact match for a curated template or example | Enabled |
| `documented` | Prefix matches a Cisco documentation entry only | Disabled |
| `unknown` | Not in the local catalog | Disabled |

Each answer gets a summary banner, and each command line gets its own label. While the check is running,
Fill is disabled and the line reads **Checking the local catalog…**. If the check fails, the command is
treated as `unknown` and the UI says to verify it on the device.

**Strict command grounding** is on by default (`Settings → AI → Strict command grounding`). In strict mode,
documentation-only syntax may be explained but is never presented as a runnable command, and reference
entries are excluded from the free-chat command hints.

Explicit command requests (“what command shows interface errors?”, “command to capture traffic”) are not
sent to the model. The composer button changes to **Find command** and opens the command browser with the
question as the query, so the answer comes from the catalog and the deterministic router.

Unknown commands remain visible so you can still discuss them, but they cannot be filled. Copying and
saving a snippet are always available; neither action runs anything.

### Automatic hybrid setup

When the command reference is opened with the AI assistant enabled, a local Ollama profile, and
**Download local models automatically** on, TSTerm:

1. checks for `nomic-embed-text`,
2. pulls it through Ollama if it is missing,
3. builds the vector index for the 503 fillable records in the background.

The command browser can also run the same check manually with **Build vector index**. Turning the setting
off skips the automatic background setup; the manual build still works when `nomic-embed-text` is already
installed.

### Thinking tokens

Ollama requests use `think: false` so Qwen3 does not spend the answer budget on hidden reasoning.
DeepSeek R1 gets a larger `num_predict` because it always thinks. Any literal `<think>` or `<thinking>`
blocks are removed from both streamed and final text, including tags split across stream chunks.

## Router contract

The router is implemented in `src/main/commands.ts` and only uses a local Ollama provider. Qwen3 8B is
the default because it won the 300-question ASA benchmark: **289/300 (96.3%)** with a **197 ms** median,
versus DeepSeek R1 8B at 285/300 but a **3.8 s** median and weak cleanup answers. See
`benchmarks/asa-model-benchmark.md`.

1. Retrieve candidate records with hybrid search **over fillable records only**.
2. Prefer complete runbook steps over top-level command entries and never offer documentation-only
   reference entries.
3. Send the candidates, the question, and optional terminal output to Ollama with a JSON schema.
4. The model returns only:

```json
{
  "command_id": "asa.rb.capture-host.0",
  "params": { "iface": "outside", "src": "10.1.1.1", "dst": "8.8.8.8" },
  "missing_required_params": [],
  "confidence": "high",
  "reasoning": "The request names a host-to-host capture on the outside interface."
}
```

5. Reject any `command_id` that is not in the candidate list.
6. Reject any parameter name that is not declared by the selected record.
7. Drop any value that does not appear verbatim in the question or terminal output. Model-provided
   addresses, interfaces, and names are not trusted.
8. Validate every value against its regex and reject control characters.
9. Render the command from the template in application code.
10. Retry once only when the JSON or selected ID is invalid; missing values become form fields.

The returned result never contains model-authored command syntax. `rendered` is present only when all
required values are present.

## Safety model

| Risk | Examples | UI behavior |
| --- | --- | --- |
| `read_only` | `show`, `ping`, `dir` | Green note; output can still be large or sensitive |
| `diagnostic` | `debug`, `capture`, `packet-tracer` | Amber note; cleanup is shown when recorded |
| `mutating` | `configure`, `write`, `clear` | Amber warning; review before filling |
| `destructive` | `reload`, `erase`, `delete`, `format` | Requires typing `CONFIRM` before Fill |

Fill always writes exactly one line and never sends Enter. The AI has no terminal, SSH, file, or IPC
execution access.

Terminal output is passed as untrusted data inside a fenced block. The router prompt explicitly says not
to follow instructions found in it. Values extracted from it still go through the same regex and
provenance checks.

## Using it

- Menu: **Session → ASA Command Reference** (`Ctrl+Shift+J`).
- Command palette: **ASA command reference**.
- AI panel: the **Commands** chip opens the browser with the current draft as the query.
- AI panel: an explicit command request changes **Ask** to **Find command** and opens the browser directly;
  the free-chat model is not called for command lookup.
- Command answers mark every command as verified, documented, or unknown; only exact curated matches can be
  filled.
- Search by command, keyword, symptom, interface, or exact token.
- Filter by risk.
- Select a fillable record, fill parameters, review the preview, then **Fill**, **Copy**, or **Snippet**.
- Documentation reference entries show the documented syntax and a **Cisco doc** link; they can be
  copied but not filled.
- Incomplete top-level records are clearly labeled and cannot be filled until you add the subcommand or
  pick a complete runbook step.
- **Let AI choose** appears when AI is enabled and a local Ollama model is selected.

## Data and test commands

```bash
# Regenerate the curated fillable catalog from the ASA pack and command index
node scripts/build-asa-command-catalog.mjs

# Re-import the Cisco ASA command reference (network access required)
node scripts/import-asa-command-reference.mjs

# Fast unit tests (no Ollama)
npm test

# Opt-in vector + Qwen3 router tests (real Ollama)
$env:TSTERM_OLLAMA_TEST = '1'
npm test -- tests/commands-ollama.test.ts

# Command browser UI smoke (no SSH host required)
node scripts/commands-ui-smoke.mjs

# Also build the vector index and verify the hybrid footer
$env:TSTERM_BUILD_VECTORS = '1'
node scripts/commands-ui-smoke.mjs
```

The opt-in test builds the 503-record embedding index, checks semantic retrieval for VPN, RADIUS,
certificate, and interface questions, and verifies that Qwen3 8B:

- routes a host-to-host capture without inventing values;
- routes a RADIUS question to an AAA command;
- keeps a reload/delete request in the `destructive` risk class.

## Known limitations

- The catalog is ASA-only and version-labeled 9.24; other versions and platforms are not modeled yet.
- Top-level commands are incomplete by design. The UI labels them and prefers runbook steps for routing.
- Literal ASA-help examples are browsable and copyable, but excluded from AI routing so example IPs or
  ports can never be substituted for the user's values.
- The 2,510 Cisco reference entries are documentation aids, not parameterized recipes. Their syntax is
  normalized from Cisco's HTML tables; verify unusual bracket/pipe formatting against the linked page.
- Assistant grounding trusts the local catalog. If the catalog lacks a valid version-specific command, the
  command is marked unknown and cannot be filled until the catalog is extended (for example from live ASA
  `?` help).
- Grounding checks the rendered text against curated templates and examples. A command with substituted
  values is verified only when it matches a template's structure.
- Syslog IDs are tokenized and searchable, but the reference import does not yet map IDs to commands.
- The router currently requires a local Ollama provider. Cloud providers remain available for free chat.
- Qwen3 8B is the recommended router. A 3B model may produce valid JSON but weaker candidate selection.
- Vector index rebuilds are manual after the catalog changes. The cache reuses unchanged records.
